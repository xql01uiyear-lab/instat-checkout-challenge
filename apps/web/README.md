# @checkout/web — фронтенд оформления заказа

React + TypeScript + Vite. Каталог, серверная корзина, оформление с расчётом
доставки, тестовая оплата картой с идемпотентностью, опросом статуса и
восстановлением после перезагрузки.

## Запуск

Требуются Node.js 24.x и npm 11.x (см. корневой `README.md`). Из свежего клона:

```sh
npm ci                       # ставит зависимости всех воркспейсов, включая apps/web

# 1) API (порт 4000) — в одном терминале:
npm run dev                  # из корня репозитория: собирает contracts и поднимает API

# 2) Фронтенд (порт 5173) — в другом терминале:
npm run dev -w @checkout/web
```

Откройте <http://localhost:5173>. Гостевая сессия создаётся автоматически.

Сборка и проверка типов фронтенда:

```sh
npm run build -w @checkout/web      # tsc --noEmit + vite build
npm run typecheck -w @checkout/web
```

Если API работает на другом порту, задайте адрес через переменную окружения:
`VITE_API_URL=http://localhost:4100 npm run dev -w @checkout/web`.

> Типы API берутся напрямую из `packages/contracts` (tsconfig `paths` указывает на
> исходники), поэтому отдельная сборка contracts для фронтенда не нужна.

## Архитектура

```
src/
  api/
    http.ts        единственное место с fetch: базовый URL, заголовки, авторизация,
                   сериализация, проверка статуса, пустой ответ, разбор конверта
                   { data }, нормализация ошибок, обновление сессии при 401
    errors.ts      ApiError — один нормализованный вид ошибки (network | http | parse)
    endpoints.ts   типизированный каталог: api.orders.create(...) и т.д.
    session.ts     хранение токена (localStorage), переживает перезагрузку
  lib/
    useAsync.ts    useAsyncData (загрузка с отменой) и useMutation (Result<T>, guard)
    poll.ts        общий опрос с отменой через AbortController + Retry-After
    idempotency.ts стабильный ключ идемпотентности (reset на новую попытку)
    useForm.ts     общее поведение полей: значения, ошибки, touched, валидация
    validation.ts  правила по одной реализации (email, phone, minLength…)
    money.ts       единое форматирование копеек
  ui/controls.tsx  Button, TextField, RadioCard, Spinner, ErrorNote (доступность, состояния)
  features/
    cart/          CartContext (серверная корзина — источник истины), QuantityStepper
    catalog/       HomePage (каталог + корзина)
    checkout/      CheckoutPage, delivery.ts (построение delivery, расчёт готовности)
    order/         OrderPage (успех/оплата), CardPayment, useCardPayment (жизненный цикл)
```

**Слой API.** Компоненты не знают о HTTP. `http.request` централизует базовый URL,
заголовки, `Authorization`, сериализацию тела, `Idempotency-Key`, проверку статуса,
обработку `204`/пустого тела, разбор конверта `{ data, meta, links }` и приведение
любой ошибки к `ApiError`. При `401` из-за сброшенной сессии токен пересоздаётся один
раз и запрос повторяется. `endpoints.ts` — тонкий типизированный слой поверх; новый
запрос добавляется одной декларацией.

**Ошибки.** `ApiError` — размеченное объединение `network | http | parse`. Доменное
состояние (например, `paymentStatus = failed` при HTTP 200) — это данные, а не ошибка:
оно проходит как обычный результат. Компоненты показывают `error.message`, связывают
`error.info.fields` с полями формы или предлагают повтор — но не разбирают `Response`.

**Состояние.** Серверное состояние не дублируется: корзина, quote, заказ и платёж
всегда читаются от сервера. После изменения количества/удаления `CartContext`
перечитывает корзину (`GET /api/cart`) — итоги и версия приходят с сервера. Локальное
состояние (поля формы, выбранный способ) — обычные хуки. Redux/Zustand не нужны.

**Идемпотентность.** `POST /api/orders` и `POST …/payments` используют
`Idempotency-Key`. Ключ сохраняется при повторе после **сетевой** ошибки (тело и ключ
те же → сервер вернёт уже созданный ресурс) и сбрасывается при успехе или новой попытке
(после отказа/отмены — новый ключ).

**Опрос и отмена.** `poll()` — один цикл «прочитать → подождать `Retry-After` →
прочитать», управляемый `AbortController`. Опрос платежа прекращается при завершении,
размонтировании и смене заказа; поздний ответ отбрасывается (проверка `signal.aborted`),
поэтому не подменяет более свежее состояние.

**Перезагрузка.** Токен и `currentOrderId` — в `localStorage`. Страница заказа
`/order/:id` при монтировании читает заказ и список попыток, находит активную и
продолжает опрос. Новая оплата из-за перезагрузки не создаётся.

**Успех — от сервера.** Успешный `POST` оплаты не считается успехом заказа. Страница
успеха читает заказ и показывает успех только при `status = paid` и
`paymentStatus = succeeded` (для наличных — `confirmed`).

## Производительность — разбор одного участка

`features/cart/CartContext.tsx` строит индекс позиций один раз на изменение корзины:

```ts
const itemsById = useMemo(() => {
  const map = new Map<string, CartItem>();
  if (cart) for (const item of cart.items) map.set(item.productId, item);
  return map;
}, [cart]);
```

- **Частота:** пересобирается только при новой корзине (после загрузки или мутации), а
  не на каждый рендер и не на каждую карточку товара.
- **Проходы/память:** один проход по позициям, одна `Map`. Каталог (`HomePage`) при
  рендере каждой карточки делает `itemsById.get(id)` за O(1) вместо `items.find(...)` на
  каждый товар (иначе O(товары × позиции) на каждый рендер).
- `HomePage` так же одним проходом строит `stockById` вместо `products.find` при каждом
  обращении корзины к остатку.
- Обновление количества заменяет весь объект корзины (сервер — источник истины), но это
  единственная необходимая копия: промежуточных `map().filter()` и лишних клонов нет.

## Проверенные сценарии

Проверено вручную против запущенного API и сверено с `npm run smoke` (проходит):

- Каталог загружается; недоступный товар (`clock-dot`, stock 0) нельзя добавить.
- Добавление, изменение количества (до лимита остатка), удаление; итог совпадает с API.
- Пустая корзина: оформление недоступно.
- Самовывоз (выбор пункта) и курьер (адрес); стоимость доставки и итог — из quote API.
- Бесплатная доставка курьером от 5 000 ₽ (порог сервера) отражается в итоге.
- Оплата картой: успех (`succeeded` → страница успеха), отказ (`CARD_DECLINED`),
  отмена — с возможностью повторить оплату тем же заказом (новая попытка, новый ключ).
- Наличные: заказ `confirmed`, сообщение об оплате при получении, без онлайн-оплаты.
- Двойной клик по «Оформить»/«Оплатить»: дублей нет (ref-guard + `Idempotency-Key`).
- Перезагрузка во время обработки оплаты: опрос продолжается, новая оплата не создаётся.
- Сетевой сбой: форма и введённые данные сохраняются; повтор возможен.
- Ошибки валидации от API связываются с полями формы.

## Известные ограничения

- Конфликт версии корзины/устаревший quote обрабатывается сообщением «подтвердите
  заказ ещё раз» (данные обновляются, форма сохраняется); автоматического повторного
  оформления нет — так безопаснее, если изменилась сумма.
- Дизайн намеренно минималистичный (приоритет — корректность и архитектура).
- Тесты фронтенда не входят в задание; поведение проверялось вручную и через `smoke`.
